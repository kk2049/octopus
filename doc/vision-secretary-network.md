# 愿景归档 — 秘书 Agent 网络（Secretary Agent Network）

> **历史文档。** 归档 2026-07 秘书 Agent 网络的原始愿景，不是当前实现规格；修改现有秘书或汇报能力时从相关包级文档与代码进入，只在核对产品意图时回读本文。

> 记录人: Claude Code ｜ 归档日期: 2026-07-15
> 本文件是**产品愿景的原始归档**，不是实现方案。实现路径的调研与分析见同目录后续文档 / 对话。

---

## 1. 一句话愿景

**让每个人都有自己的私人秘书（agent）。汇报不再是人对人甩只言片语，而是"秘书对秘书"先把事情勾兑清楚，再让老板在充分理解的前提下对话。**

---

## 2. 愿景的原始叙述（用户原话精神）

> 大老板之间讨论业务，从不直接面对面硬碰。都是秘书先勾兑好了、让大老板提前搞明白，才正式讨论的。
>
> 在当今年代，agent 就应该承担这个秘书的工作。
>
> 所以当有人给我汇报的时候，**不要让他直接给我写那些只言片语的话**，而是让他先启动一个秘书 agent，然后给秘书 agent 描述需求；让秘书 agent 调查最近的各种 Claude Code / Codex 的 session、看相关文件，掌握到底是什么个事情。然后把相关材料、沟通内容、以及自己这方的判断，发送给对方的 agent 秘书。然后对方的 agent 秘书，结合对方工作区里面的已有信息，按照对方用户偏好的汇报形式，总结一个材料。

---

## 3. 核心工作流（汇报的一次"勾兑"）

```
汇报方                                         接收方
──────                                         ──────
1. 启动秘书 agent
2. 向秘书描述需求（要汇报什么）
3. 秘书调查：
     - 最近的 Claude Code / Codex session
     - 相关文件
     → 掌握"到底是什么事"
4. 秘书打包：材料 + 沟通内容 + 己方判断
                    │
                    │  秘书 → 对方秘书
                    ▼
                                   5. 对方秘书接收材料
                                   6. 结合"对方工作区已有信息"补全上下文
                                   7. 按"对方用户偏好的汇报形式"总结
                                   8. 产出：给接收方老板看的成品材料
```

关键点：
- **调查是自动的**：汇报方秘书主动去翻 session/文件，而不是等人手工整理。
- **判断是带上的**：秘书传递的不只是原始材料，还有"己方判断"。
- **落地是本地化的**：接收方秘书用**接收方自己工作区的上下文** + **接收方偏好的格式**来重新组织，而不是原样转发。
- **人只在"充分理解"后才介入**：秘书之间先把信息势能拉平。

## 4. 两条接入路线（用户设想）

| 路线 | 场景 | 直觉 |
|------|------|------|
| **A. 飞书 bot** | 日常沟通、老板侧阅读成品材料、审批 | 前端交互逻辑重，天然是"人读材料"的界面 |
| **B. Claude Code / Codex skill** | 干完活后**直接在 code agent 窗口里提交汇报** | 汇报方就在 IDE/终端里工作，不用切界面 |

两条路都要能**触发同一套秘书流程**。

## 5. 架构直觉（用户的初步猜想，待验证）

用户尚未确定实现，但给出了几点直觉：

1. **需要一个独立的中心进程**，负责与飞书后端握手。
2. **用户的 Claude Code session 分散在不同机器上** → 需要**多个前端头**，部署在各用户机器，负责：
   - 获取本地 agent 的历史 session；
   - 作为 skill 的**通讯管道**（skill 大概很难直连中心进程）。
3. **类似 frp 的系统**：用户启动自己的本地进程，与中心进程握手反连。
4. **多用户 × 每用户多进程**：一个用户可能有多台机器 / 多个连上来的进程。

### 用户自己识别出的"最麻烦、可共用"的部分
- 与飞书握手的这一段（飞书侧有大量前端交互逻辑）；
- 驱动 LLM 推理的这一段。

## 6. 待解决的核心问题（本次调研要回答的）

1. **自研 vs 开源**：现有这套自研代码库（OpenClaw 等价物，已实现部分飞书交互）够不够好？有没有更轻量、更完善、更好魔改的开源项目能省掉"飞书握手 + 驱动 LLM"这两段？
2. **从"实现效果"和"可维护性"两个角度**，最优实现路径是什么？
3. 需要魔改出一套**用户系统**，且**每个用户绑定一堆进程**——在选定的底座上，这件事容易还是难？

---

## 7. 与现有代码库的初步呼应（记录，非结论）

现有 `octopus` 代码库里，以下能力已与愿景高度重合，值得作为"是否复用"的评估基础：
- **WebSocket 前端头 + token 认证**（`channel/websocket.ts`）——已有"独立前端进程连中心"的雏形。
- **SSH 反向隧道 + 端口分配**（`workspace/manager.ts`、`cli/cli.py`）——已是"frp 式反连"的实现。
- **Workspace 项目级隔离**（每个 user×remote×workdir 一个 workspace）——已是"多用户多进程"的骨架。
- **MCP over tunnel + 本地 MCP daemon**（`remote-mcp-server/`）——已能让中心 agent 反向访问本地机器文件。
- **Delegate 子任务 / agent 间委派**（`plugins/delegate/`）——与"秘书之间互发材料"机制相近。
- **飞书群自动创建 + 卡片交互 + OAuth**（`channel/feishu*.ts`）——飞书前端已有相当积累。

> 这些呼应意味着：愿景的"分布式骨架"可能已存在，真正待补的是"秘书语义层"（调查—打包—跨秘书投递—按偏好落地）。具体成熟度与 gap 由本次三路调研给出结论。
